CHAPTER 3: SYSTEM DESIGN AND ARCHITECTURE

3.1 System Overview

NTTH implements an agent-inspired modular autonomous pipeline consisting of five processing phases connected through an asynchronous event bus. The system captures network traffic from both wired interfaces (using Scapy packet capture) and wireless interfaces (using the AR9271 adapter in monitor mode), analyzes each packet through a hybrid detection engine, and autonomously enforces appropriate responses through Linux kernel firewall rules and honeypot redirections.

The design philosophy follows the principle of defense-in-depth, where multiple layers of security mechanisms work together to provide comprehensive protection. Unlike traditional IDS systems that operate as passive monitors, NTTH acts as an active security gateway positioned inline with the network traffic, enabling it to not only detect but also enforce defensive actions in real-time.

The system operates in two complementary modes. In gateway mode, the host machine acts as a network bridge (br-ntth) connecting KVM virtual machines and real devices, giving NTTH full visibility into all forwarded traffic. In monitor mode, the AR9271 USB WiFi adapter captures 802.11 management frames for wireless threat detection. Both modes feed into the same unified processing pipeline.

3.2 Agent-Inspired Pipeline Design

We adopt an agent-inspired architecture where each processing stage operates as an autonomous module following the classical perception-reasoning-action pattern defined by Russell and Norvig. Each stage perceives inputs from the event bus, reasons about appropriate responses using its specialized logic, and takes actions within its domain.

The agent-inspired design provides several architectural advantages over monolithic IDS systems. First, fault isolation: if the enforcement agent encounters an error applying a firewall rule, the threat detection and reporting agents continue functioning normally. Second, independent scalability: each agent can be profiled and optimized independently. Third, testability: each agent can be unit-tested with synthetic event bus messages without requiring a live network.

3.3 Asynchronous Event Bus

The processing stages communicate through a publish-subscribe event bus implemented using Python asyncio queues with a capacity of 5,000 events. This decoupled design ensures fault isolation — if one stage fails, others continue processing. The event bus uses a single-threaded asyncio event loop for dispatching, ensuring thread safety without requiring explicit locking.

The event bus implements back-pressure handling through its bounded queue. When the queue reaches capacity (5,000 events), new publications are dropped with a warning log, preventing memory exhaustion under sustained attack traffic. Events are dispatched in FIFO order, maintaining temporal ordering of security decisions.

3.4.2 Rule Engine Detectors

The rule engine implements seven sliding-window detectors that operate on per-source-IP bounded deques. Each detector maintains a time-windowed history of events and calculates a score in [0.0, 1.0] based on whether observed activity exceeds defined thresholds.

3.4.3 Isolation Forest Anomaly Detection

The machine learning component uses scikit-learn's Isolation Forest algorithm configured with 100 estimators and a contamination parameter of 0.05 (5% expected anomaly rate). The model is trained on baseline normal traffic and produces anomaly scores in the range [-1, 1], which are normalized to [0, 1] for combination with the rule score.

The key advantage of Isolation Forest for our use case is that it is unsupervised — it does not require labeled attack data for training. Instead, it learns the statistical distribution of normal network traffic and flags deviations. This makes it suitable for deployment in networks where attack data may not be available for training, and it can detect novel zero-day attacks that rule-based systems would miss.

3.4.4 Combined Scoring Formula

risk = 0.6 × rule_score + 0.4 × ml_score

The weights (0.6 for rules, 0.4 for ML) were determined through empirical testing. The rule-based component receives higher weight because it provides deterministic, interpretable decisions for known attack patterns. The ML component provides coverage for novel attacks that rules cannot detect. A confidence boost mechanism raises the combined score to a minimum of 0.90 when a rule detector achieves maximum confidence (rule_score = 1.0), ensuring that confirmed attacks always trigger enforcement actions.

3.5 Flow-Aware Dynamic Honeypot Deployment

Unlike static honeypots that are deployed before attacks occur, NTTH creates targeted NAT redirection rules for specific network flows in real-time. When the Decision Agent determines a honeypot response, the Enforcement Agent creates an iptables DNAT rule scoped to the bridge interface:

iptables -t nat -I PREROUTING -i br-ntth -s {attacker} -d {victim} -p tcp --dport {port} -j DNAT --to-destination {gateway}:{honeypot_port}

This provides three key advantages:

  1. Selective deception: Only the attacker's malicious traffic is redirected; legitimate traffic passes normally.
  2. Dynamic activation: Honeypot rules are created in response to detected threats, not pre-configured.
  3. Contextual correlation: Each honeypot session is linked to the original threat assessment through a redirect context registry.

The system only creates DNAT rules for well-known service ports (22, 23, 80, 443, 3306, 3389, 5432, 5900, 8080) to prevent pollution of iptables with rules for random nmap probe ports. SSH-like ports (22, 23, 3389, 5900) are redirected to Cowrie (port 30022), while HTTP ports (80, 443, 8080) are redirected to the custom HTTP honeypot (port 8888).

3.5.1 Honeypot Intelligence Escalation

When an attacker is redirected to the Cowrie SSH honeypot, the session logger tracks per-attacker command counts. The system observes attackers for their first 10 command interactions ("Log Only" mode) to gather threat intelligence — including login credentials, commands executed, malware URLs downloaded, and lateral movement attempts. After 10 interactions, the system autonomously escalates to a "Block" action, terminating all further communication from the attacker's IP address.

This two-phase approach maximizes intelligence gathering while limiting attacker exposure time, addressing the finding by Vetterl and Clayton that 72% of SSH honeypot sessions last less than 60 seconds.

3.6.1 Data Retention and Cleanup

The system implements automatic data lifecycle management. Firewall rules have configurable TTLs (default: 1 hour for rate limits, 24 hours for blocks) and are automatically deactivated by a scheduled background task. Captured packet metadata is retained indefinitely for forensic analysis, while device statistics are aggregated into 5-minute snapshots to manage storage growth.
